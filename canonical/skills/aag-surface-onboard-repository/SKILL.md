# Onboard a repository into the workspace

## Purpose

Register one repository as a root of an existing `.code-workspace` file and give it folder-level editor settings that point at the repository's own runtime and pinned tools, so the editor reports what that repository's CI reports and nothing CI would not. The procedure is language-agnostic; stack-specific evidence and candidate settings are in `toolchain-profiles.md` beside this file. Success means the workspace file lists the folder, every path named in the folder settings resolves to a working binary of the pinned version, every key written is contributed by an installed extension at a folder-settable scope, the settings stay out of Git, and the other roots are unchanged.

## Procedure

1. Select the local target editor (`cursor` or `code`) and, if applicable, confirm an existing named profile before passing `--profile`. Remote extension hosts are unsupported. Establish the inputs: the repository path and the workspace file. The workspace file is the `*.code-workspace` in the repository's parent directory (for example `~/git/git.code-workspace`); if several exist, or none, stop and ask. Confirm the repository is a Git checkout with `git -C "<repo>" rev-parse --show-toplevel` and record `git -C "<repo>" status --short --branch`. Preserve pre-existing work.
2. Read the workspace file. From this skill directory run `python3 validate_jsonc.py <workspace-file>` before editing. Preserve comments and unrelated content with targeted edits. Record the existing `folders` order and the window-level `settings` block. Window-level keys are shared by every root and were chosen for reasons that hold across roots (for example a type checker kept off because roots pin different versions of it, or because CI uses a different checker). Do not change existing window-level values. If the block is absent, report it rather than inventing one.
3. Inventory the repository's toolchain from its own files, not from another root. Identify the stack from its detection files, then read the matching profile in `toolchain-profiles.md` and answer its five questions with evidence: the pinned runtime version and where a persistent copy lives; the command CI runs (`.github/workflows/*`, `.gitlab-ci.yml`, `Makefile`, `tox.ini`, `package.json` scripts, solution files) and the tools it calls in order; the project-local pinned copies of formatter, linter, and type checker and the lockfile that pins them; module roots the task runner adds and vendored or generated trees to keep resolvable but silent; and any checker the editor would run that CI does not. A repository may match several profiles; a stack with no profile is recorded as unprofiled and handled with the same questions, without guessing setting names.
4. Derive the candidate settings from that inventory. For every key, run `python3 setting_scopes.py --editor <cursor|code> [--profile <existing-name>] <key> ...` from this skill's directory. Keep a key only if it is found and marked `folder-ok`; a `NOT-FOUND` key is unknown, not proof of a missing extension. Report unknown keys, ambiguous declarations, and discovery errors without guessing. A `NOT-FOLDER` key cannot live in folder settings; only a declared window scope is a candidate for window settings. Core settings need no contributing extension, but verify the formatter extension named by `editor.defaultFormatter` separately. For a window-only key the new root needs, check whether the existing roots would want a different value. If not, propose the addition to the workspace `settings` block and report it as a separate decision; if they would conflict (one window, several pinned versions), leave it unset and record which roots conflict. Do not surface editor-only diagnostics that CI does not run: teammates and CI would never see them.
5. Check for an existing `.vscode/settings.json`. If `git -C "<repo>" ls-files --error-unmatch .vscode/settings.json` succeeds the file is tracked: do not overwrite it or add an exclude entry; compare it with the derived settings and report differences. If an untracked file exists, validate it with `validate_jsonc.py`, then merge derived keys while preserving unrelated settings and comments. Tracked settings bypass steps 6–7; report differences only.
6. Make the paths the settings will name exist before the editor reads them. Install the pinned runtime with the user's version manager only when it is missing, and report the install. Build project-local tooling the way the profile describes (tox environment, `npm ci`, `dotnet tool restore`, `rustup` toolchain) without running the test or lint suite itself. Base every environment on a persistent runtime location, never on a path under `/tmp`, a shell-dependent version-manager shim, or another project's virtual environment; such bases leave dangling symlinks or silently change later. Inspect dependency installation hooks first: installation is not inherently side-effect-free. Run only setup commands whose effects fit the allowed scope; otherwise report the specific blocker.
7. For untracked settings that require changes, write or merge the keys kept in step 4, using `${workspaceFolder}` for paths. Add `.vscode/` to `.git/info/exclude` unless `git -C "<repo>" check-ignore -q .vscode/settings.json` already succeeds. Do not edit the repository's `.gitignore`. A repository whose inventory shows no editor-relevant tool gets no file; report that outcome.
8. Resolve existing folder paths relative to the workspace file and skip insertion if the repository is already present. Otherwise add `{ "path": "<repo-name>" }` to `folders` in the workspace file, keeping the existing ordering convention (alphabetical in `~/git/git.code-workspace`). Leave `settings` untouched unless step 4 produced an approved window-level addition. Validate with `python3 <skill-directory>/validate_jsonc.py <workspace-file>`.
9. Verify against the recorded starting state, preserving pre-existing work. For newly written or merged settings, validate with `python3 <skill-directory>/validate_jsonc.py <settings-file>`, verify configured binaries exist and print the expected versions, and require `git check-ignore -v .vscode/settings.json` to identify an effective ignore rule (repository, local exclude, or global). Do not add a redundant rule. For tracked settings, confirm the bytes are unchanged and report differences; skip exclusion checks. When no editor-relevant settings are needed, create no file and skip file-dependent checks. Compare final Git status with the starting state. Use the selected editor and existing profile for extension verification; installed status does not establish activation or runtime loading. Failed applicable checks are blockers, not permission to relax verification.
10. Compare the new root's pinned tool versions with the other roots' for every window-only tool (type checkers, language-server SDKs). If all roots now agree, report that the window could enable that tool; do not change the window settings in this task.

## Boundaries

- Change only the new repository's `.vscode/settings.json`, its `.git/info/exclude`, its ignored dependency and environment directories, and the `folders` list of the workspace file. Do not edit existing window-level `settings` values, user settings, other roots, project manifests, lockfiles, CI files, or `.gitignore`.
- Derive every setting from the repository's own files. Do not copy another root's settings file or apply one language's layout to a repository of another.
- Write only keys whose scope was confirmed with `setting_scopes.py`. Do not invent or recall setting names for extensions that are not installed.
- Do not run the repository's test or lint suite as part of onboarding; environment creation uses setup-only commands, with required dependency installation separated from check hooks.
- Installing or removing editor extensions is outside this task. Report missing ones.
- Never create commits, push, or touch tracked files. A tracked `.vscode/settings.json` is reported, not replaced.
- A window reload is required before the editor uses the new settings; report it rather than performing it.
- When the stack is unprofiled, report it so `toolchain-profiles.md` can be extended; do not extend it in the same task without the user's request.

## Completion

- The workspace file path and the added `folders` entry; confirmation that `settings` is unchanged, or the approved window-level addition.
- The detected stack and profile(s), and the written `.vscode/settings.json` with one line per key stating the file and line that chose it, its scope, and its extension; or the reason no file was created.
- Runtime and tool versions installed or built, each against its pin and persistent location.
- Verification results from step 9, the exclude entry, and `git status` for the repository.
- Window-only tool comparison across roots, missing extensions, unprofiled stacks, and any blocker.
